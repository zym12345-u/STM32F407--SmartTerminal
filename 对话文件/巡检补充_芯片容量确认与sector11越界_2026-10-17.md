## 一、结论

用户已确认开发板芯片为 **STM32F407VET6** → **512KB Flash，地址上限 0x0807FFFF，物理上只有 sector 0~7**。

因此 `bsp_WifiStore.h:23` 的 `WIFI_FLASH_BASE 0x080E0000` 与 `bsp_WifiStore.c:71` 的 `FLASH_SECTOR_11` **越界，不是"待核实"，是实锤缺陷**。

## 二、为什么 HAL 不报错（这点最关键）

`Drivers/STM32F4xx_HAL_Driver/Inc/stm32f4xx_hal_flash_ex.h`：

```c
/* 771-773 行 */
#if defined(STM32F405xx) || ... || defined(STM32F407xx) || ...
#define FLASH_SECTOR_TOTAL  12U      /* ← F407xx 一律按 12 扇区(1MB 布局)处理 */
#endif
```

HAL 把 F405/F407 整族都当成 1MB，`IS_FLASH_SECTOR(FLASH_SECTOR_11)` 为**真**。所以 `HAL_FLASHEx_Erase` 会对不存在的扇区照常发起擦除，**不会有任何断言或错误返回**——这是一个静默失败。

## 三、后果链（与现网症状吻合）

```
擦 sector11(不存在) → 无实际效果 / 行为未定义
  → HAL_FLASH_Program 写到 0x080E0000(未实现地址)
  → memcmp 回读不等 → WifiStore_Save() 返回 0
  → 下次 WifiStore_Load(): stored->magic != 'WIFI' → 返回 0
  → 表现为「配网成功但重启不记忆」
```

这条正好对应 `esp8266-wifi-screen-debug/SKILL.md` 排错表的「连接成功但重启不记忆」项。但该表给的原因写的是「sector11 与 IROM 重叠被擦」，**这个解释不成立**：实测代码止于 `0x0807A0A8`，与 `0x080E0000` 根本没有重叠。真因是地址越界。

我已把该 skill 条目订正（标注 2026-10-17 巡检订正）。

## 四、对你手头 D3 草案的影响（重要，请重读这一条）

我上一封给你的 RLR 放宽草案，前提是「擦除 128KB 内部扇区期间 CPU 停取指」。

**若凭据改存外部器件，这个前提会变**：

| 载体 | 擦除时 CPU 是否停取指 | RLR 放宽是否仍必要 |
|---|---|---|
| 内部 Flash（现状） | 是（单 bank） | **必要** |
| W25Q128（SPI） | **否**——是外设操作，CPU 照常跑 | 可改用"周期喂狗"替代，更简单 |
| TF 卡（SDIO） | **否** | 同上 |

所以**先定存储载体，再定 D3 的修法**，否则可能白做。我的建议：

1. 凭据迁到 W25Q128（板载 16MB，V1.2 本就要接）→ 内部 Flash 只放代码
2. 迁移后 D3 改用「擦写循环里周期喂狗」，比改 RLR 更干净，且不存在"放宽后真死等 6s"的代价
3. 若你坚持留在内部 Flash，则仍按我上一封草案执行，但**必须先解决"没有空闲扇区"**——见下

## 五、附带发现：内部 Flash 已无空闲扇区可划给数据

按本次 map：`Total ROM Size = 499,944 B` → 代码止于 `0x0807A0A8`，**占用贯穿 sector 0~7**，尾部仅剩约 **23.8KB**。

也就是说：**就算把地址改对，VET6 上也找不到一个完整空闲扇区放凭据**（擦任何一个 128KB 扇区都会擦掉代码）。

唯一的内部 Flash 解法是：把代码压进 sector 0~6（≤384KB），把 sector 7 整块让给数据。需要减掉约 105KB。

## 六、减重杠杆（数据出处：本次 map）

| 项 | 大小 |
|---|---|
| `lv_font_gb2312_16` glyph_bitmap | 198,435 B |
| 同字体 glyph_dsc | 61,936 B |
| unicode_list_1 + 3 | 7,516 B |
| **字库合计** | **≈ 268,000 B（262 KB）** |
| 其余全部代码 + RO | ≈ 232,000 B（227 KB） |

**更正我上一封的一个数字**：我说 `--bpp 2 → 1` 能省约 130KB，**这个数错了**。bpp 只影响 `glyph_bitmap`，`glyph_dsc` 与 unicode 表不变，实际节省约 **99 KB**（198,435 → ≈99,218）。更正后总账：

- 现状：488.23 KB
- bpp=1 后：约 **389 KB**，仍比 384KB 上限高约 5KB，**单靠 bpp=1 不够**
- 需再配合小幅裁剪字符集（或把凭据放外部器件，则不必压到 384KB）

## 七、给你的任务单（预估成本：低）

1. **顺手验一下**：打印 `*(uint16_t *)0x1FFF7A22`（Flash size data register，单位 KB）。若是 512 则本文件所有结论坐实；若是 1024 则说明芯片与丝印不符，我再改口径。一行代码的事。
2. 决定凭据载体（W25Q128 / TF 卡 / 留在内部 Flash），我据此确认 D3 修法。
