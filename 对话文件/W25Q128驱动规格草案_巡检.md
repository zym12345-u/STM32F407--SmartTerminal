## 0. 先读这一节：三个会让第一里程碑跑偏的点

### 🚩 0.1 最要紧：你要的 `0xEF4018` 厂商例程根本读不出来

**厂商 `readID()` 用的是 `0x90`（Read Manufacturer/Device ID），不是 `0x9F`（JEDEC ID）。**

- 出处：`bsp_W25Q128.c:159` `sendByte(0x90);`
- 该命令返回 **2 字节**：`0xEF` + `0x17` → 拼成 `Temp = 0xEF17`
- 厂商宏定义印证：`bsp_W25Q128.c:24` `#define W25Q128 0XEF17`

而 **JEDEC ID `0xEF4018` 必须用 `0x9F`，读 3 字节**（`0xEF`=Winbond / `0x40`=Memory Type / `0x18`=2²⁴=16MB=128Mbit）。

> **照抄厂商 `readID()`，永远读不到 `0xEF4018`。** 第一里程碑必须新写一个 `0x9F` 版本。

建议两个都读、都打印，互为交叉验证：`0x90`→`0xEF17` + `0x9F`→`0xEF4018`，两个都对才叫链路真通。

### 🚩 0.2 厂商 `WaitReady()` 没有超时 —— 会死循环咬狗

`bsp_W25Q128.c:90-98`：

```c
static void WaitReady()
{
    W25Q128_CS_LOW;
    sendByte(0x05);
    while (sendByte(0xFF) & 1) {}    /* ← 无超时、无心跳 */
    W25Q128_CS_HIGH;
}
```

Flash 未焊/损坏/CS 线断 → 永远退出不来 → **IWDG 复位**。这正是 D3 那套"心跳空窗"问题的同类。必须重写（见第 4 节）。

### 🚩 0.3 厂商开了 42MHz，第一里程碑建议降速

厂商 `bsp_W25Q128.c:302` `BR[5:3] = 0` → `fPCLK/2` = 84MHz/2 = **42MHz**。
第一里程碑的目标是"链路通"不是"跑满速"，建议先用 `PRESCALER_8`（10.5MHz），读到 ID 后再逐级试 21M / 42M。

## 1. SPI 初始化参数

出处：`bsp_W25Q128.c:299-307`（厂商直接写 `SPI1->CR1`）

| 项 | 厂商值 | HAL 对应写法 | 备注 |
|---|---|---|---|
| 时钟极性 CPOL | **1**（空闲高） | `SPI_POLARITY_HIGH` | `#define W25Q128_SPI_AFx GPIO_AF5_SPI1`（.h:64） |
| 时钟相位 CPHA | **1**（第 2 边沿采样） | `SPI_PHASE_2EDGE` | CPOL=1+CPHA=1 = **Mode 3** |
| 主从 | 主 | `SPI_MODE_MASTER` | |
| 波特率 | `fPCLK/2` = 42MHz | `SPI_BAUDRATEPRESCALER_2` | **建议里程碑用 `_8`(10.5MHz)** |
| 位序 | MSB 先 | `SPI_FIRSTBIT_MSB` | |
| NSS | 软件（SSM=1, SSI=1） | `SPI_NSS_SOFT` | ✅ 确认软件控制 |
| 数据位宽 | 8 位 | `SPI_DATASIZE_8BIT` | |

**关于 Mode 3**：W25Q128 同时支持 Mode 0(0,0) 与 Mode 3(1,1)。厂商用 Mode 3 且在这块板上实测可用 → **建议沿用 Mode 3 保持一致性**，除非你另有理由改 Mode 0。

### 引脚（出处：`bsp_W25Q128.h:60-76`）

| 信号 | 端口/引脚 | AF |
|---|---|---|
| SCK | PA5 | AF5 |
| MISO | PA6 | AF5 |
| MOSI | PA7 | AF5 |
| CS | **PC13**（GPIO 输出推挽、上拉） | — |

**冲突复核（我已逐项核过本工程，结论：无冲突）**：

| 引脚 | 现状 | 是否冲突 |
|---|---|---|
| PA5/PA6/PA7 | 空闲（PA0/1 按键、PA2/3 ESP、PA9/10 调试、PA15 背光） | ✅ |
| PC13 | 空闲。**注意 XPT2046 的 CS 是 `PD13` 不是 PC13**（`bsp_XPT2046.h:66-67` `GPIOD`/`GPIO_PIN_13`） | ✅ |
| GPIOC 整体 | LCD FSMC 只用了 **GPIOD**(0,1,4,5,7,8,9,10,11,14,15) 与 **GPIOE**(7-15)（`bsp_LCD_ILI9341.c:141,148`），**GPIOC 未参与 FSMC**；GPIOC 现仅 PC1(DHT11)、PC5(led_green) | ✅ |

⚠️ **一个待核实的隐患**：PC13/14/15 属**备份域**引脚，ST 对其 GPIO 有驱动能力与速度档限制（约 3mA、输出速度上限较低）。**本地无 W25Q128/STM32 数据手册，无法给手册出处**。
**但我判断此处无风险**：CS 仅在每次 SPI 事务时翻转一次（页编程 256B 一次），翻转频率远低于 MHz 级；且负载仅 Flash 的 CS 输入（高阻）。
**兜底**：若第一里程碑读不到 ID，把 CS 临时改到 PC0/PC2~PC4/PC6~PC12（均空闲）做交叉验证，可快速区分"SPI 参数错"还是"CS 引脚问题"。

## 2. 命令序列表

记号：`CS↓`=拉低、`CS↑`=拉高、`A[23:16]/A[15:8]/A[7:0]`=地址三字节（W25Q128 用 3 字节地址；W25Q256 才是 4 字节）

| 操作 | 命令 | 完整字节流 | 出处 |
|---|---|---|---|
| **读 JEDEC ID** ⭐ | **0x9F** | `CS↓` → `9F` → 读 3 字节（`EF`/`40`/`18`）→ `CS↑` | **厂商例程无**，需新写 |
| 读厂商/设备 ID | 0x90 | `CS↓` → `90` → `00` `00` `00` → 读 2 字节（`EF`/`17`）→ `CS↑` | `bsp_W25Q128.c:158-165` |
| 写使能 | 0x06 | `CS↓` → `06` → `CS↑` | `bsp_W25Q128.c:82-84` |
| 读状态寄存器 1 | 0x05 | `CS↓` → `05` → 持续读字节直到 `bit0(BUSY)=0` → `CS↑` | `bsp_W25Q128.c:93-96` |
| 读数据 | 0x03 | `CS↓` → `03` → `A3` `A2` `A1` → 读 N 字节 → `CS↑` | `bsp_W25Q128.c:332-343` |
| 页编程 | 0x02 | 先单独 `06` → `CS↓` → `02` → `A3` `A2` `A1` → **≤256 字节** → `CS↑` → 轮询 BUSY | `bsp_W25Q128.c:133-145` |
| 扇区擦除 4KB | 0x20 | 先单独 `06` → `CS↓` → `20` → `A3` `A2` `A1` → `CS↑` → 轮询 BUSY | `bsp_W25Q128.c:109-119` |
| 块擦除 32KB | 0x52 | 同 4KB 结构（命令字节换 0x52） | **厂商例程无**，按手册 |
| 块擦除 64KB | 0xD8 | 同 4KB 结构（命令字节换 0xD8） | **厂商例程无**，按手册 |
| 写状态寄存器 | 0x01 | `06` → `CS↓` → `01` → 1~2 字节 → `CS↑` → 轮询 BUSY | **厂商例程无**，按手册 |

**三个易错点**：

1. **页编程不能跨页**：单条 `0x02` 最多 256 字节，且**不能跨越 256 字节页边界**（跨页会从页首回卷）。厂商注释明确写了（`bsp_W25Q128.c:129`），其 `writeSector` 按 16 页×256B 拆写（`bsp_W25Q128.c:131`）
2. **写使能是每条写/擦命令前都要发**，且它本身是一次独立 CS 事务（不能和 `0x02`/`0x20` 合并）
3. **厂商 `eraseSector(uint32_t addr)` 的参数其实是"扇区号"不是字节地址** —— 内部 `addr = addr * 4096`（`bsp_W25Q128.c:107`）。而同文件 `writeSector(secPos*4096, ...)` 传的是字节地址（`bsp_W25Q128.c:384`）。**两个函数参数语义不一致**，移植时极易写错，建议重命名为 `eraseSectorByIndex()` / `writeSectorByAddr()` 之类

## 3. 时序上限表（看门狗窗口设计依据）

### ⚠️ 先声明出处缺口

**本地没有 W25Q128 数据手册**。网盘 `1、芯片文档` 只有 `STM32F4xx_参考手册_1/2.pdf`（ST 的），没有 Winbond 的。所以**本节只有 1 个数字有本地出处，其余为估算**，请以手册为准后再用。

| 操作 | typ | max | 出处 |
|---|---|---|---|
| 4KB 扇区擦除 | — | **> 150 ms** | ✅ **有本地出处**：`bsp_W25Q128.c:102` 注释「擦除一个扇区, 每扇区>150ms」 |
| 页编程 256B | ~0.4 ms | ~3 ms | ❌ **估算（无本地手册）** |
| 32KB 块擦除 | ~120 ms | ~1.6 s | ❌ **估算（无本地手册）** |
| 64KB 块擦除 | ~150 ms | ~2 s | ❌ **估算（无本地手册）** |
| 写状态寄存器 | — | ~15 ms | ❌ **估算（无本地手册）** |
| 整片擦除 | — | 数十秒 | ❌ **估算（无本地手册）**，**不要用** |

> **请从 Winbond W25Q128JV 数据手册 "AC Electrical Characteristics" 表核一遍再定稿。** 之前你说"有机会补数据手册"，这个就是最需要的场景。

### 但设计上可以不依赖这些数字

**关键做法：用 BUSY 轮询而非固定延时**。轮询循环自身就是实测计时器——

```c
uint32_t t0 = HAL_GetTick();
... 轮询 BUSY ...
uint32_t elapsed = HAL_GetTick() - t0;   /* 顺手打印,可回填上表 */
```

**建议第一里程碑就把 `elapsed` 打出来**，几次擦写后就能拿到本板的真实 typ 值，反过来填表，比抄手册更贴合这颗料。

## 4. FreeRTOS 适配：心跳策略（基于 D3 教训）

### 4.1 与内部 Flash 的根本区别

| | 内部 Flash 擦除 | W25Q128 擦除 |
|---|---|---|
| CPU 状态 | **停取指**（单 bank，擦时不可读） | **正常运行**（SPI 外设操作） |
| 能否在等待中喂狗 | **不能**（代码跑不了） | **能** ✅ |
| 结论 | 必须放宽 RLR（V1.1.1 的 `IWDG_SetReload`） | **原则上不必放宽**，在轮询里喂心跳即可 |

所以你 V1.1.1 那套 `IWDG_SetReload(RELOAD_FLASH_SAVE=500)` **在 W25Q128 上大概率用不上**——但建议保留兜底，见 4.3。

### 4.2 推荐的 `WaitReady` 写法（同时修掉厂商无超时的坑）

严格套用你 V1.1.3 总结的两条铁律：**入口必报 + 长循环节流**。

```c
HAL_StatusTypeDef W25Q_WaitReady(uint32_t timeoutMs)
{
    uint8_t  st;
    uint32_t t0 = HAL_GetTick();

    Watchdog_Heartbeat(WDT_TASK_STORAGE);        /* ① 入口必报:防快响应路径零心跳 */
    W25Q_CS_LOW();
    (void)W25Q_SpiByte(0x05U);
    do {
        st = W25Q_SpiByte(0xFFU);
        if ((st & 0x01U) == 0U) {                /* BUSY 清零 */
            W25Q_CS_HIGH();
            return HAL_OK;
        }
        Watchdog_Heartbeat(WDT_TASK_STORAGE);    /* ② 循环内补报 */
        osDelay(1);
    } while ((HAL_GetTick() - t0) < timeoutMs);

    W25Q_CS_HIGH();
    return HAL_TIMEOUT;                          /* ③ 必须有超时,不能死等 */
}
```

三条缺一不可：
- **① 入口必报** —— V1.1.3 教训：快响应（BUSY 立即清零）时若只在循环里报，整次调用零心跳
- **② 循环内补报** —— 慢响应时防长时间空窗
- **③ 超时** —— 厂商没有，会死循环咬狗

超时建议值：`timeoutMs` 取 表 3 中对应操作 **max 值 × 2**（4KB 擦除先取 **800ms**，等实测后收紧）。

### 4.3 何时仍需 `IWDG_SetReload`

- 若后续用 **32KB/64KB 块擦除**（估算 max 1.6~2s），单次调用可能超过 1s 窗口 → 建议仍套 `IWDG_SetReload(500)` 兜底
- 若只用 **4KB 扇区擦除**（>150ms，远小于 1s）→ **不需要放宽**，喂心跳即可
- **建议 V1.2 只暴露 4KB 扇区擦除给上层**，既简化也避开窗口问题

### 4.4 其他 RTOS 注意

1. **SPI1 互斥**：虽然当前只有 W25Q128 一个 SPI1 设备，但文件系统会被多任务调用 → 加 `osMutex`，或**统一由单一 StorageTask 串行访问**（我倾向后者，与现有"LVGL 只被 GUITask 单线程调用"的风格一致）
2. **不要照抄 `W25Q128_buffer[4096]`**（`bsp_W25Q128.c:357`）—— 4KB 全局数组，在当前 RAM 预算下太贵（ZI 已 94668、稳态堆仅 4.8KB）。LittleFS 自带 cache，不需要它
3. **LittleFS 挂载的 RAM 开销（估算）**：`block_size=4096`、`prog_size/read_size=256`、`cache_size=256`、`lookahead_size=128` → 单 fs 约 **0.5~1KB**。
   ⚠️ **A1 扩堆到 32KB 之前不要上 LittleFS** —— 现在稳态只有 4.8KB，挂上去很可能直接崩
4. **W25Q128 容量 16MB / 4KB = 4096 blocks**，LittleFS `block_count=4096`

## 6. 附加发现（超出派活范围，但影响 V1.2 路线，请裁决）

### 6.1 板载 W25Q128 尾部已烧录 GBK 字库 → 可能释放 262KB 内部 Flash

出处：`bsp_W25Q128.h:30-34,58`

```
GBK_STORAGE_ADDR 0x00A00000     // 宋体 12/16/24/32 号字模
地址范围 0x00A00000 ~ 0x01000000（后 6MB）
```

检测函数 `checkFlagGBKStorage()`（`bsp_W25Q128.c:203-222`）就是在验这个。

**这意味着**：目前吃掉内部 Flash 52% 的 `lv_font_gb2312_16`（**262KB**，见 Bug 复盘手册 B-008）**有可能整体下线**，改用 W25Q128 上的字库。

- **M2**：跑一遍字库存在性检测（等价 `checkFlagGBKStorage`），确认这颗料真的烧了字库

## 8. 建议的里程碑划分（供你排期）

| 里程碑 | 验收标准 | 依赖 |
|---|---|---|
| **M1**（你定的） | 真机读出 `0x9F` → **`0xEF4018`**（并同时打印 `0x90`→`0xEF17` 交叉验证） | 本草案第 1、2 节 |
| M1.5 | 扇区擦除 + 页编程 + 回读校验通过，并打印**实测耗时**回填第 3 节表 | M1 |
| M2（建议加） | 字库存在性检测通过 | M1 |
| M3 | LittleFS 挂载 + 读写 | **A1 扩堆 32KB 必须先做** |

⚠️ **顺序提醒**：A1（堆扩到 32KB）应在 M3 之前完成，否则 LittleFS 的 ~1KB 开销落在只剩 4.8KB 的稳态堆上有风险。
