IWDG 寄存器讲解
对照 bsp_IWDG.c 逐行 · 全部行号可回查 · 静态速查页
先建立一个心智模型：把 IWDG 想成焊在芯片旁边的另一个小芯片——它有自己的振荡器（LSI）、自己的计数器，只把"复位输出"这根线连到你的 MCU 复位脚上。你的 CPU 跑 168MHz，它在旁边用自己的 32kHz 慢悠悠数数。你唯一能做的事是隔一段时间拍它一下说"我还活着"。它不听你解释，也不受你控制。
这个模型立刻解释了三件事：为什么要用独立时钟、为什么写它的寄存器要等同步、为什么一旦启动就关不掉。
①四个寄存器
IWDG 总共只有 4 个寄存器：KR PR RLR SR。
KR Key Register · 只写
不接受数据，只接受魔数命令：
  • 0xCCCC 启动 —— 之后无法关闭
  • 0xAAAA 喂狗（把 RLR 装回计数器）
  • 0x5555 解锁 PR / RLR 的写保护
为什么用魔数而不是普通寄存器？防跑飞的代码误喂狗。如果喂狗是"往某地址写 1"，跑飞后乱写内存时有很大概率命中；而要求写一个特定的 32 位魔数，纯靠乱写撞中的概率是 1/2³²。
出处 bsp_IWDG.c:29 / :50 / :32
PR Prescaler · 低 3 位
分频 = 4 × 2^PR，取值 0~7 → 4 / 8 / 16 / 32 / 64 / 128 / 256 / 256。
注意最小分频是 4，不是 1。
为什么非要有它：RLR 只有 12 位（max 4095），用最小分频时最长只有 4×4096/32000 ≈ 512ms，Flash 擦除 2s 根本装不下。
PR 定量程，RLR 调细度。本工程 PR=6（/256）。
出处 bsp_IWDG.c:15
RLR Reload · 低 12 位
喂狗时硬件把它装进递减计数器，数到 0 就复位。T ≈ 分频 × (RLR+1) / f_LSI。
手册多一个 +1：RLR=125 → 1.008s（代码注释写 1.0s，差 0.8%）。推论：RLR=0 不等于立刻复位（本工程配置下最短约 8ms）。
运行时可改（V1.1.1 的关键）：改写后必须「等 SR + 补喂一次」，否则新值要等下次喂狗才生效。
出处 bsp_IWDG.c:16,38,57-63
SR Status · 只读
bit0 PVU 预分频更新中 · bit1 RVU 重载值更新中。
为什么要等它：PR/RLR 在 LSI 时钟域，CPU 在 HCLK 时钟域，跨时钟域写入需同步（LSI 只有 32kHz，一个周期 31µs）。这就是 while (IWDG->SR != 0U) 存在的原因。
出处 bsp_IWDG.c:41,61
① 启动顺序里有一个真实陷阱 —— 对照 bsp_IWDG.c:29-44：
IWDG->KR = 0xCCCCU; /* ① 启动 */ IWDG->KR = 0x5555U; /* ② 解锁 */ IWDG->PR = IWDG_PRESCALER_256; /* ③ 配分频 */ IWDG->RLR = IWDG_RELOAD; /* ④ 配重载 */ while (IWDG->SR != 0U) { } /* ⑤ 等同步 */ IWDG_Refresh(); /* ⑥ 首次喂狗 */
写 0xCCCC 的瞬间狗就以上电默认值开始跑了 —— 那时 PR 还是 0（分频 4）、RLR 还是 0xFFF，超时约 0.5 秒。也就是说：启动之后必须在 0.5s 内把配置写完并喂第一口，否则配置还没配完就被自己咬死。本工程这段代码紧接着执行所以没事，但你要是在中间插个 printf 或延时，就可能踩到。
⚠️ 顺带指出一个隐患：bsp_IWDG.c:41 和 :61 这两处 while (IWDG->SR != 0U) { } 都是无超时死等。LSI 没起来或坏了 → RVU 永不清零 → 卡死在 IWDG_Init() 里 → 而此时 0xCCCC 已写、狗已在跑 → 必然复位 → 重启又卡在同一处 → 无限复位循环，串口可能什么都打不出来，极难定位。这和厂商 WaitReady() 那个空 while 是同一类毛病。

③独立时钟 LSI 的意义与代价
IWDG 由 LSI（内部低速 RC，典型 32kHz）驱动，不经过 PLL、不依赖 HSE。
故障用 PCLK 驱动的"假狗"LSI 独立的 IWDG
HSE 晶振停振❌ 时钟没了狗也停，系统死了却永不复位✅ 照常数数，复位
PLL 失锁 / RCC 配错❌ 同上✅
程序跑飞乱改 RCC❌✅
单纯死循环✅✅
一句话：如果狗和 CPU 共用一套时钟，那"时钟挂了"这个最常见的死法，狗是看不见的。这就是"独立"唯一、也是全部的意义。
所以 bsp_IWDG.c:25-26 第一步必须先开 LSI 并等 LSIRDY —— 不等它稳定就启动 IWDG，等于"你以为有狗，其实没有"。
代价清单：
  • ① 精度差 → 超时只是标称值，必须留余量（见 ② 的计算器）。
  • ② 跨时钟域 → 写 PR/RLR 要等 SR 同步，不立即生效（见 ① 的 SR 卡片）。
  • ③ 关不掉 → 一旦 0xCCCC，除复位外无法停止；调试时用 DBGMCU_APB1_FZ 的 DBG_IWDG_STOP 让调试暂停时计数器也停。bsp_IWDG.h:13
  • ④ 低功耗要小心 → IWDG 不跟着 CPU 睡，STOP 期间仍在数，唤醒后可能已超时。
④WWDG：喂太早也复位
本工程只用 IWDG（Core/App/Bsp/ 下只有 IWDG/），WWDG 是概念对比，但面试高频。
IWDG 的盲区
IWDG 只问「你还活着吗」—— 只要超时前喂过就行，1 毫秒喂一次它也接受。
但如果程序跑飞进一个野循环，而循环里恰好有一句喂狗 → 系统早已不正常，IWDG 却一直被喂，永远不复位。
WWDG 补的那半边
多一条规矩：喂得太早也复位。计数器 7 位从 0x7F 递减，另有窗口上限 W：
  • 计数器 > W 时喂 → 太早，复位
  • 0x40 ≤ 计数器 ≤ W 时喂 → 通过
  • 计数器跌到 0x3F → 硬件直接复位
喂狗时机反映执行节奏：跑飞后跳过代码会喂太早，卡住会喂太晚，两边都抓。

代价：WWDG 要求喂狗间隔严格落在窗口内，调度一抖就可能误复位。所以本工程用 IWDG + MonitorTask 软件心跳 是更合适的组合 —— 用软件让一个"只能看整体死活"的 IWDG，具备了"知道是哪个任务死了"的能力：
/* bsp_IWDG.c:73-93 */ uint8_t Watchdog_CheckAllAlive(void) { for (i = 0U; i < WDT_TASK_MAX; i++) { if (i == WDT_TASK_MONITOR) continue; /* 监控者不监控自己 */ if (s_lastBeat[i] != 0U && (now - s_lastBeat[i]) > pdMS_TO_TICKS(3000U)) /* 3s 未心跳 = 卡死 */ return 0U; /* 停喂 → IWDG 复位 */ } return 1U; }
复习路径：
  1. ① 记住心智模型：IWDG 是旁边那个"不听你解释"的小芯片。它解释了独立时钟、SR 同步、关不掉这三件事。
  2. ① 背 KR 三个魔数：CCCC 启动 / AAAA 喂狗 / 5555 解锁。想一遍"为什么是魔数"。
  3. ① 记住启动后只有 0.5s 配置窗口这个坑，以及两处 while(SR) 无超时的隐患。
  4. ② 把 PR 拨到 0，看档位上限只有 512ms → 理解为什么必须有 PR；再把 RLR 拨到 125 / 500 对照本工程两档。
  5. ② 把 LSI 拨到 47kHz，看 4s 窗口缩到 2.7s 仍大于擦除 2s → 理解"余量怎么算"。
  6. ③ 能说出"共用时钟的狗看不见时钟故障"这句话。
  7. ④ 能说清 IWDG 与 WWDG 的区别：一个问"还活着吗"，一个连"节奏对不对"都要管。
